# 旧样板升级安全方案（B05-P02 拉面店、B05-P05 公寓、B05-P01 便利店）

状态：方案，未实施。起草日期：2026-10-06。读者：项目负责人与后续实施 Agent。

## 1. 目标与边界

把三栋「实心壳体」旧样板重建为与其余 35 栋一致的新建筑：独立模块 `buildings/<地块>.js`、真实墙厚与门窗洞口、可剖视的屋顶/楼层、室内连通、合批、登记 `shelter`、通过 C12。

不变量（任何一步都不得破坏）：

- 冻结布局 v1：道路、地块、可建包络、入口坐标、街道设施、电杆电线、水洼派生数据全部不动。
- 三栋门的**世界坐标**不变（路灯、电杆避让区由它派生）。
- 统一尺度 1，只用平移和 90° 倍数旋转，不用非等比缩放。
- 其余 35 栋的实测包围盒、截图和行为不变。
- 名称与身份保留：こもれび MART、雨音らーめん、こもれび荘；便利店仍是全城暖光视觉锚点，不能被升级版抢走或削弱。

## 2. 已核实的现状与风险

| # | 事实（来源） | 风险 | 对策 |
| --- | --- | --- | --- |
| R1 | 三栋在 `layout.js` 的 `samples`，新建筑在 `buildings`。C7 要求 `plot.sample===id`，C12 要求 `!plot.sample`；两个登记不能共存，同一地块不能两栋并存（重叠检查） | 无法在 main 上「新旧并行」预览 | 在功能分支上整栋切换；模块文件未登记前是惰性的（build.py 会嵌入，但场景只加载已登记的） |
| R2 | 便利店代码散在 scene.js 多处：第 27–81 行、147 行（落水管，同属 `store` 分组）、40 行 `doors` 与 45 行 `sign`（`frame()` 里驱动开合与闪烁）、341–342 行 `drops`/`drips`、323 行 `L.samples.find(s=>s.id==='store')` 的湿路面灯光倒影 | 把便利店移出 `samples` 后，323 行会得到 `undefined.transform`，**页面直接报错**；直接删代码还可能带走相邻的街道设施 | 分两步：先「退役」（移出场景，代码保留），验收通过后再单独提交「清理」；清理前先给 323 行加守卫 |

| R7 | 旧样板门不在局部原点（便利店门 (1.84,1.80)、拉面 (6.9,1.04)、公寓 (0.9,−4.88)），新模块约定门中心为原点 | 换原点后门的世界位置偏移，路灯/电杆避让区变化，C12 报错 | 新模块用门原点，`transform` 反算使 `toWorld(door)` 与现值逐位相同；用冻结数据比对确认 |

| R9 | 推送 main 会触发 Cloudflare 自动部署 | 半成品上线 | 全程在分支开发，验收通过才合并到 main；不推送中间状态到 main |

## 3. 安全原则

1. **分支隔离**：每栋一个分支 `upgrade/<地块>`，main 始终可发布。
2. **基线先行**：动手前打标签 `pre-sample-upgrade`，并固化一份基线（见阶段 0）。
3. **一轮一栋、先易后难**，每栋一个可独立回滚的提交（模块与登记）加一个「退役」提交；全部完成后再做一次「清理」提交。
4. **新增优先于修改**：新建 `buildings/<地块>.js`；对 scene.js 与 layout.js 只做最小、可逆的改动。
5. **证据靠数据**：每个门槛都对应一条命令和判定，不靠「看起来没问题」。
6. **不虚报**：SwiftShader 的帧时间不代表真机；真机项保持「待验证」。

## 4. 阶段计划

### 阶段 0：基线与工具（一轮，约半天）

不改任何画面，只增加安全网。

1. 打标签 `pre-sample-upgrade`。
2. 新增 `tools/frozen_diff.mjs`：载入 `git show <ref>:layout.js` 与当前 `layout.js`，逐项比对导出数据（`roads`、`furniture`、`poleLines`、`puddles`、`legacyFurniture`、`grates`、`plots`、`samples`、`buildings`），只允许白名单里的键变化。目前这个比对每轮手工做，这里固化。
3. 记录基线：`node tools/measure_samples.mjs` 的分组实测值、默认/正面/远景视角的绘制调用与三角形、全部 `tools/views.mjs` 结果。存入 `docs/buildings/sample-upgrade-baseline.md`。
4. 确认 `layout_check`、`measure_samples`、`building_views`、`live_topdown` 在 `samples` 为空数组时不崩（先在临时副本里把 `samples` 置空跑一遍，修工具而不是改数据）。
5. 为 323 行的灯光倒影加守卫（`L.samples.find(...)` 找不到时跳过），单独提交；对现有画面应无影响。

门槛：基线文档提交；`frozen_diff` 对 `HEAD` 自比较全绿；全部检查与阶段前一致。

### 阶段 1：B05-P02 雨音らーめん（最小耦合，先验证流程）

理由：只有 `ramen` 与 `ramenPlants` 两个分组，没有全局动画、没有街道设施牵连，占地余量最大。

### 阶段 2：B05-P05 こもれび荘

理由：耦合低，但改动最大（正确层高、三层、真实室内与外楼梯）。今天的楼梯专项是为实心壳体做的，升级时会被取代，其参数（踏步、平台、扶手）只作约束参考，不照搬。

### 阶段 3：B05-P01 こもれび MART（耦合最多、视觉锚点，放最后）

此时流程已在前两栋验证。额外处理 R2 的全部项：`doors` 自动门、`sign` 闪烁、`drops`/`drips`、灯光倒影、落水管；新版要继承这些表现（自动门间歇开合、招牌微闪、湿路面灯光倒影），可以改进但不能减少。

### 阶段 4：清理（一轮，仅在三栋都合并且观察稳定之后）

删除 scene.js 里已退役的旧样板代码与 `samples` 空列表依赖，更新文档（§6），废止 `SAMPLE_REVIEW_AGENT_START.md`。按 R3、R4 的规则精确删除。

## 5. 每栋的替换流程

在分支 `upgrade/<地块>` 上：

1. **读**：AGENT_START.md 的「先读」清单、任务卡、`references/<地块>.jpg`（升级概念图，要看图）、`screenshots/<地块>/`（现状）、BUILDING_SPEC。参考图只管外观，冲突时以任务卡与 layout.js 为准。
2. **粗模**：新建 `buildings/<地块>.js`（惰性），门用局部原点，反算 `transform` 使门的世界坐标不变。
3. **登记**（一个提交）：layout.js 中从 `samples` 移到 `buildings`，补 `module`、`floor`、`floors`、`shelter`；地块改为 `sample: null, building: '<id>'`；`parts` 写实测值。
4. **退役**（同一提交里的 scene.js 小改动）：在旧代码构建完成后，把该旧样板的分组从场景摘除（只摘除，不删代码）。便利店额外确认 R2 各项没有报错。
5. **细化**：外立面四面完整、室内三层深度、局部动画 1–3 处、不新增实时光源，沿用 kit 工具与 `bake()`。
6. **验收**（§6 全部通过）。
7. **文档**：任务卡改为已实现并写实施记录；`catalog.json`、`BUILDING_QUEUE.md`、`GALLERY.md`、`docs/buildings/README.md`、`docs/layout/LAYOUT_V1.md`、根 README 建成数量、PROGRESS（含性能差值）。
8. **合并**：全部通过后合并到 main。是否推送由负责人决定；推送前再跑一遍 §6。

每栋全部满足才合并：

| 门槛 | 命令 / 方法 | 判定 |

| 实测 | `node tools/measure_samples.mjs` | 本栋记录值与实测一致；**其余全部分组记录值与基线一致**；页面无错误 |
| 布局 | `node tools/layout_check.mjs --png` | C1–C12 全部 PASS，C12 列出本栋；主体在可建包络内 |
| 冻结数据 | `node tools/frozen_diff.mjs pre-sample-upgrade` | 只有 `plots`（本栋一条）、`samples`、`buildings`、`structures` 变化；门世界坐标逐位一致 |
| 交互与动画 | `node tools/views.mjs` | 全部 PASS，无控制台错误（含信号灯相位、漫游） |
| 单栋视图 | `node tools/building_views.mjs <地块>` | 无页面错误；局部动画在动；八视图含真实剖视（屋顶/楼层分层） |
| 参考包 | `node docs/buildings/check_kit.mjs` | 通过 |

## 7. 默认裁决（可推翻）

- **D1 重建而非缩放**：层高、柜台、吧台按新建筑标准（柜台 0.85–1.05，门净高 2.0–2.2）重建，身份与配色保留。
- **D2 公寓高度**：三层按约 2.7 层高重建，含屋顶不超过 9.5（地块限高 12）。升级后在默认、正面和远景视角各检查一次对便利店窗面的遮挡；若遮挡，降到两层半或收窄体量，而不是移动建筑。
- **D3 分支而非 main**：见原则 1。
- **D4 单栋可停**：任何一栋卡在 R5/R6，可保留旧样板进入下一栋，阶段 4 只清理已升级的。
- **D5 外楼梯**：公寓新楼梯按真实层高重算踏步与平台，侧门做成真实门洞并通到室内；今天的 `apartmentStairFlights` 随旧壳体退役。

## 8. 回滚

- 任一栋：在 main 上 `git revert` 该栋的「登记+退役」提交即可恢复旧样板（旧代码在阶段 4 之前始终保留）。
- 阶段 4 之后：回到 `pre-sample-upgrade` 标签。
- 回滚后重新运行 `python3 build.py` 并确认 `index.html` 与源码一致。

## 9. 停止条件

出现以下情况停下并报告，不自行扩大范围：

- 需要修改冻结布局、入口或可建包络才放得下；
- 门的世界坐标无法保持；
- 其余 35 栋任一实测记录发生变化；
- 默认视角绘制调用超出 §6 预算且 `bake()` 后仍不能压回。
